# AI短剧制作工作流｜项目展示

面向 AI 短剧、漫剧和剧情带货视频的流程设计与工程验证项目。将剧本采用、分镜、资产、音色、生成、实片诊断、剪辑与验收连接为可追踪的制作流程。

本仓库供项目交流和面试展示，仅公开项目概述与验证摘要。完整技能、提示词规则、实现源码和内部审查记录保留在私有仓库，不在此分发。

## 项目关注的问题

- 跨阶段交接容易丢失人物、道具、空间和对白约束。
- 模型审查建议可能误读原规则，需要逐条复现与独立裁定。
- 已核正文与实际待提交正文需要绑定，避免修改后沿用旧审核或提交授权。
- 自动检查、用户采用、安装同步与实片质量是不同的验收范围。

## 工作内容与方法

由项目发起者确定制作要求与授权边界，通过 AI 辅助实施和独立模型审查迭代。核心工作包括：需求约束整理、审查意见裁定、最小修正、回归验证、历史版本保留，以及私有维护源和公开展示材料分离。

技术涉及 Python、SQLite、Git、Markdown 规则组织、命令行离线校验与内容哈希绑定。这个项目强调的是可核实的流程与工程控制，不把生成式 AI 的自评当作完成证据。

## 版本演进

- v1：保留原始技能作为审查基线。
- v2：修正文本传输容错与已成立的设计问题，保留原始正文绑定要求。
- v3：完善提交文本边界与回归验证。
- v4：中止的实验副本，未作为发布基线。
- v5：从 v3 整理维护索引与记录措辞，避免增加逐卡验收负担。
- v6：在 v5 基础上修正画内文字与对白的语言检查边界，并关闭测试中的 SQLite 连接。

这些是既有审查快照；归档提交的时间是导入时间，不用于冒充历史开发日期。

## 可讨论的工程取舍

1. 为什么解析层容错不应放宽实际提交正文的完整性绑定？
2. 如何区分审查发现、实现建议和用户已经明确保留的规则？
3. 如何在减少重复文档的同时保留生成前检查与用户逐卡验收时序？
4. 为什么公开展示仓库与私有实现仓库采用独立历史？
